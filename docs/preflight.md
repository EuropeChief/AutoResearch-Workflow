# 轻量阶段预检

进入阶段、关键动作前或影响性修改后，运行只读入口。没有输入时直接列出缺口；不创建任务状态，不运行 Docker、模型或训练。

```bash
python cli.py --format json preflight --task-root <题目根> --stage 4
python cli.py --format json preflight --task-root <题目根> --stage 4 --before dual_track_launch --inputs <已有证据引用.json>
python cli.py --format json preflight --task-root <题目根> --stage 4 --phase exit --inputs <已有证据引用.json>
```

`--before` 使用[阶段视图](../rules/stages/)中的动作标识：研究合同、任务实现、锚点冻结、双轨启动、最佳复验、独立 QA。其中只有研究合同、锚点冻结、双轨启动需要专家明确确认；其他动作不是新增审批。阶段退出检查结果义务；双轨启动前只核日志、轨迹、计时和恢复的准备及短探针，不索要尚未产生的长轨迹。

## 三个专家决定

1. `research_contract`：确认优化面、任务范围、指标、候选 B/R 方向与协议草案，不提前冻结未经验证的锚点。
2. `anchor_freeze`：证据与 Baseline 专项审查满足后，共同确认 B/R、U 和正式评分协议。
3. `dual_track_launch`：综合预检通过后，确认实际双轨配置、合法可见范围及适用时长，再启动正式迭代。

输出分开给出 `checks_ready`（到期检查/审查已满足）、`confirmations_ready`（对应专家决定记录有效）和 `ready`（两者均满足）。机器通过不自动生成批准。新题的正式实现读取研究合同确认；锚点冻结读取研究确认；双轨启动读取前两项及本次启动确认。尚待确认时可继续准备与定位缺口，不启动对应正式动作。

需要确认时，Agent 根据 `confirmations[].proposal` 向专家简要说明实际选择、证据和限制；收到真实明确答复后，才将该 proposal 的规则版本、文件引用和 bindings 连同确认人、范围、限制追加到 `.autoresearch/decision-log.md`。模板见[决定记录](../templates/decision-log.example.md)。路径和哈希由程序产生，专家不用填写；同一文件可支撑多项绑定，优先引用已有稳定合同/汇总，不绑定会不断追加的运行日志。

读取时核当前规则版本、绑定文件的路径/哈希及最新决定。已有确认且范围未变就直接复用；后续阶段可以读取原记录中的文件引用，不要求重复抄入全部输入。最新拒绝、无效或过期记录不能退回沿用旧批准。源文件有变化时先由 Agent 判断实质影响、定向复核，再请求必要的更新确认；不因此自动重训、重开全部阶段或停止健康轨迹。

程序只能核记录，不能认证确认人身份；不得由 Agent 自行写“专家批准”。决定不替代费用、Docker/GPU 或安全例外授权，也不能把实际检查失败覆盖为 PASS。`waived` 的决定须有真实确认、理由和完整核心证据绑定；具体检查项的跳过仍使用下面的 obligation 例外，不把整个阶段标成“已通过”。

普通操作、原会话恢复、轨迹完成后的退出审阅、最佳方法复验及独立 QA 不增加或追补启动审批。已通过独立 QA 的最终包直接使用 `package`，不运行阶段预检、不补历史决定；打包工具不读取题目决定记录。旧题目的局部返修按用户指定范围处理，不补办新流程手续。

## 引用已有结果，不另填 PASS 账本

可选 `--inputs` 是调用输入：`evidence` 将阶段视图的证据 ID 对应到已有文件；同一文件可支撑多个 ID。只读当前题目根内非空普通文件，结构化文件须可解析，显式哈希须一致。大数据/目录引用已有清单或报告，不要求重复拷贝或全目录哈希。模板见 [preflight-inputs.example.json](../templates/preflight-inputs.example.json)。

引用可附 `validator: "protocol"` 或 `validator: "trajectory"`，复用现有协议/八字段轨迹校验；不指定时只核文件格式，不能冒充方法或行为检查。启动前无需生成完整轨迹，只准备输出格式和日志方案。

机械项通过 `checks` 引用既有程序 JSON 输出；`reviews` 引用既有实质审查并注明责任人、结论和依据摘要。两者都用 `obligations` 指明真实覆盖范围，`bindings` 绑定本次检查所用证据的 SHA-256。可以一份报告覆盖多项，不为各项新建报告；引用和绑定不能扩大原报告的真实覆盖范围。程序不通过关键词推测优化面合理性，也不把文件存在等同于行为有效。

这些引用由 Agent/工具从实际文件整理，专家不必逐条登记或手工抄写哈希。启动两轨前所用短检查也只做必要合法入口，不因此另建全套攻防测试。

对机械输出，顶层成功但仍有错误/待审内容不会判完整通过；局部检查只能供其真实覆盖范围使用。`PASS` 表示引用、结构和已有结论相符，不证明重放了实际 Trial，也不替代科学审查或独立 QA。

## 结果与例外

- `PASS`：当前范围已有有效检查/审查及对应证据。
- `PENDING`：尚未到期的准备缺口、缺实质审查或动作后的结果；不要自填通过。
- `BLOCKED`：到期缺证据、已有证据错误、哈希变化或实质失败。
- `WAIVED`：专家明确确认的局部例外，不声称原要求通过。
- `NOT_APPLICABLE`：仅条件性规则有证据证明不适用；无条件规则不能据此取消。

阶段门/高成本动作前，`ready` 要求到期项均已解决；返回码 2 表示不应按默认流程继续。进入阶段的待补项不自动阻断普通工作。例外在题目 `.autoresearch/decision-log.md` 追加，格式见[决定模板](../templates/decision-log.example.md)：明确义务 ID、动作、当前 `rule_version`、原因、确认人、确认依据和限制。只有收到用户/专家真实确认后才记录；程序验证其记录，不认证人的身份。例外仍不得绕过运行权限或费用授权，且不写入最终提交包。

条件性要求可沿用有责任人和证据的 `NOT_APPLICABLE` 审查，不额外索要豁免；例如 Agent 可见面没有 `.git` 时，C02 不再造一轮清理任务。无条件规则的“无需检查”声明不能据此生效。

```bash
python cli.py --format json preflight --task-root <题目根> --stage 4 --changed M03 --inputs <已有证据引用.json>
```

`--changed` 由 Agent 根据实际影响指定 M/C 规则或义务 ID；输出相关阶段与下游读取位置作为复核提示，不持久保存 STALE、不重开全部阶段、不自动重跑。无科学/评分/可见性影响的普通文字修改无需填写。证据哈希不匹配时则会实际阻断旧检查结论。
